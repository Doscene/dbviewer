## 【修正 · 同日 14:00】根因锁定：后台状态 = `Verifying`（恶意软件扫描 + 沙箱动态检测）

上面那条「瓶颈在账号/审核层面」的说法**被推翻**。盖伦发来管理后台截图，**状态列明写 `Verifying`**，Version `0.5.0`，Updated `5 minutes ago`，Availability `Public`。

**官方机制（`https://aka.ms/vscode-extension-security` 原文）**：

- *Malware scanning*：市场对每个扩展包做多引擎病毒扫描，**"run for each new extension and for each extension update. Until the scan is all clear, the extension won't be published in the Marketplace for public usage."**
- *Dynamic detection*：在 clean-room VM 沙箱里跑一遍扩展验证运行时行为。

→ 「Verifying」= 这两步没跑完。期间 **item 页 404 / 搜索不收录 / CDN 端点 404**，全是同一个原因，**不是发布失败**。

**交叉验证（本次实测）**：

| 检查 | 结果 |
|---|---|
| 管理后台状态列 | `Verifying`（截图，决定性） |
| `extensionquery` filterType=7 精确名 | `count=0`，未收录 |
| item 页 | 404 |
| GitHub Actions run #3 | `2026-09-18T05:50:45Z`（北京 13:50）**success**，与后台 `Updated 5 minutes ago` 精确吻合 |
| 今天跑的流水线 | 3 次（`03:06` / `03:11` / `05:50` UTC），版本全是 0.5.0，全部 success |

**关键推论 —— 别再重跑流水线**：

`HaaLeo/publish-vscode-extension@v2` 的 `skipDuplicate` 默认 `false`（重复版本会 hard fail）。run #3 却是 **success**，说明它**真的又把 0.5.0 传了一遍**——即市场把「待验证/已撤下的版本」视为可重传。而扫描是**每次更新都重跑**的，所以：

> 每重跑一次流水线 = 重新上传 + **把验证计时清零**。昨天发到今天 20+ 小时还没出来，最可能就是被反复重传打断的。

（也解释了日志里 `already exists` 与「同版本又能上传」的矛盾：待验证版本在扫描未过后被撤下，于是又能重传。）

**待办 / 行动**：

1. **停止重跑流水线**，以 run #3（北京 13:50）为起点静默等待，中途不要再 publish。
2. 超 24h 仍 `Verifying` → 管理页右上角 **Contact Microsoft** / `https://aka.ms/marketplacepublishersupport` / `vsmarketplace@microsoft.com`。
3. 已排除 secret-scanning 嫌疑：解包 `dbviewer-0.5.0.vsix`（320 文件 / 2.06 MB），无 `.env` / `.npmrc` / `.git` / `.pem` / `id_rsa`。`.vscodeignore` 已覆盖 `.workbuddy/**`、`scripts/**`、`*.vsix`、`**/*.ts`。
4. 等待期自证包没问题：`code --install-extension dbviewer-0.5.0.vsix` 直装（不走市场），可确认功能本身 OK。

**教训（写进 MEMORY.md）**：判断发布状态**只看管理后台状态列**。外部探测（`vsce show` / `extensionquery` / item 页 / CDN）对 Verifying 中的扩展一律 404，**不能作为「发布失败」的判据**——今天上午就是被这个误导，得出「已入库但未公开、瓶颈在审核」的错误结论。

## 【备份功能 · 版本 0.6.0】

需求：① 右键 / 多选数据表，备份被选中的表；② 右键数据库备份整库，且驱动支持多种方式时让用户选。

**分层落点**：`core/backup.ts`（分块编排 + 多选目标收集 + 文件名/文件头，纯 Node）→ `drivers/backupCore.ts`（游标状态机 + `BackupDialect`）→ `drivers/mysqlBackup.ts` / `pgBackup.ts`（方言实现）→ `commands/backup.ts`（选方式 / 选路径 / 进度 / `FileSink` 流式落盘）→ `platform/externalTool.ts`（原生工具 `spawn`）。UI 侧 `createTreeView` 开 `canSelectMany: true`，package.json 加 `6_backup` 右键分组。

**方式声明**：`DriverDefinition.backupModes[]` 各 4 种（完整 SQL / 仅结构 / 仅数据 / 原生 `mysqldump`·`pg_dump`）。原生方式带 `scope:'database'`，被 `filterBackupModesForScope` 在表节点入口过滤掉；选中它而 `allowExternalCommand` 关闭时，提示后直接退回内置方式，不重跑命令。

**踩到并修掉的问题**：

| # | 问题 | 修法 |
|---|---|---|
| 1 | `source: driver!` 报 TS2322 —— `BackupSource` 要求 `backupChunks` 必填，而 `IDatabaseDriver` 上是可选属性；且闭包内 TS 不保留对 `let` 的收窄 | 先取 `const backupDriver` / `const backupChunks`，以 `backupChunks.call(backupDriver, request)` 保住 `this` |
| 2 | `dbviewer.backupToolPaths` **代码里读、package.json 里没声明** → 用户无法在设置里发现它 | 补进 `contributes.configuration`，并顺带修订 `allowExternalCommand` 的说明（现在也管备份工具） |
| 3 | 冒烟测试章节编号从 10 起跳（没有 9） | 顺延为 9–15 |
| 4 | 激活测试 mock 的 `withProgress` 只传进度对象、**没有** `CancellationTokenSource` → 回调里访问 `token` 会抛 TypeError 并被自身 try/catch 吞掉（测试反而「通过」） | mock 补真取消令牌 + `CancellationTokenSource` 类 |

**验证**：`npm test` 全绿 —— 冒烟 **83 项**、激活 **66 项**（原 52 / 64）。版本号提到 `0.6.0`，CHANGELOG 加 0.6.0 章节、README 加「备份」章 + 配置项表两行。**未打包、未发布** —— 0.5.0 仍在 Verifying，按既定结论不重发（重传会清零验证计时）。
